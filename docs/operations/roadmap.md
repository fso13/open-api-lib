# Ограничения и roadmap

Раздел фиксирует всё, что библиотека **не** делает или делает не так, как ожидается,
с оценкой влияния и способом обхода. Это входные данные для планирования доработок.

---

## 1. Критичные дефекты (требуют решения до продакшена)

### 🔴 1.1. Повышение привилегий через произвольные скоупы

**Что происходит.** `POST /api/openapi/tokens` принимает любые непустые скоупы и не сверяет
их ни со справочником, ни с правами владельца. В режиме `scopes.mode=identity` скоуп
становится authority без изменений, а административные эндпоинты статера требуют
`hasRole("ADMIN")` → authority `ROLE_ADMIN`.

**Сценарий.** Любой аутентифицированный пользователь создаёт токен со скоупом `ROLE_ADMIN`
и получает доступ к `/api/openapi/admin/**`.

**Обход.** Валидация скоупов по белому списку, пересечение с правами пользователя,
переход на `mapped`-режим или отдельный контур для админского API — см.
[Аутентификация](../features/security.md#повышение-привилегий-через-скоупы).

**Планируемое решение (предложение):**
- свойство `openapi.tokens.scopes.allowed` (белый список) или обязательная сверка
  с `ScopeCatalog` при создании токена;
- запрет выдачи authority, которых нет у текущего пользователя;
- отказ в создании токена со скоупом, начинающимся с `ROLE_`.

## 2. Существенные проблемы

### 🟠 2.1. Просроченные токены остаются в статусе `ACTIVE`

`markExpired()` не вызывается в production-коде; фонового задания нет. Просроченный токен
не проходит аутентификацию, но в БД и API остаётся `ACTIVE`, а статус `EXPIRED` недостижим.

**Влияние:** поддержка, отчёты и администраторы могут считать «мёртвый» токен рабочим;
в UI нельзя отфильтровать просроченные.

**Обход:** вычислять фактический статус по `expiresAt` (и `lastUsedAt + slidingTtlSeconds`);
добавить свою задачу перевода в `EXPIRED`.

**Предложение:** планировщик (по умолчанию выключенный) или вычисляемое поле
`effectiveStatus` в DTO.

### 🟠 2.2. Квота не освобождается при отзыве

`countByOwnerId` считает все токены независимо от статуса, а операции удаления токена в API
нет. Отозванные токены навсегда занимают место в квоте (`10` по умолчанию).

**Влияние:** пользователь не может выпустить новый токен «взамен» старого без обращения
к администратору/разработчику.

**Обход:** поднять `limits.max-tokens-per-owner`; удалять строки из БД вручную.

**Предложение:** считать квоту только по `ACTIVE`/`BLOCKED` или добавить операцию удаления
токена (с аудитом).

### 🟠 2.3. Мёртвые свойства конфигурации

Не читаются кодом: `audit.enabled`, `audit.async`, `audit.record-failures`,
`rate-limit.backend`, `token.default-ttl`.

**Влияние:** ложное ощущение управляемости; TTL по умолчанию не применяется, аудит нельзя
выключить конфигурацией, Redis-бэкенд «выбрать» нельзя.

**Обход:** замена бинов (`AuditRecorder`, `RateLimiter`), явная передача `expiresAt`.

**Предложение:** либо реализовать поведение, либо удалить свойства и задокументировать
замену бином (второе честнее).

### 🟠 2.4. Тенант принимается из запроса без проверки

`tenantId` из `CreateTokenRequest` записывается в токен, если он не `null`
(`command.tenantId() != null ? command.tenantId() : owner.tenantId()`).

**Влияние:** в мультитенантном контуре можно «записать токен в чужой тенант».

**Обход:** не принимать поле из внешнего API или перезаписывать значением из контекста.

**Предложение:** свойство «доверять/игнорировать тенант из запроса», сверка с владельцем.

### 🟠 2.5. Фильтр аутентификации не покрыт тестами, а цепочка безопасности не загружается в тестах

401/429, пропуск запроса без токена, установка `SecurityContext`, аудит, правила
`hasRole("ADMIN")` не проверяются. Это горячий путь безопасности.

**Обход:** покрыть своими интеграционными тестами в продукте.

**Предложение:** добавить тесты фильтра, провайдера, `ApiTokenAuthentication`,
`ApiTokenPermissionEvaluator`, `InternalTokenOwnerResolver` и HTTP-тесты готовой цепочки.

### 🟠 2.6. Нет ограничения/пагинации в административном API

`GET /api/openapi/admin/tokens` отдаёт все токены (`findAll()` с N+1 по скоупам),
без фильтров и страниц; фильтры в демо-UI считаются в памяти.

**Влияние:** при большом числе токенов — медленно и затратно.

**Обход:** ограничить использование админского API; свои выборки через JPA.

**Предложение:** добавить `Pageable`-методы в порт и параметры запроса.

## 3. Умеренные проблемы и ограничения

| # | Проблема | Влияние | Обход |
|---|---|---|---|
| 3.1 | Rate limiter in-memory; ведра не удаляются | В кластере лимит ×N узлов; рост памяти | Внешний `RateLimiter`; лимит на шлюзе |
| 3.2 | Аудит только аутентификации (нет событий создания/отзыва/блокировки) | Нельзя ответить «кто выдал токен» | Дополнять событиями продукта |
| 3.3 | Журнал аудита не ротируется | Неограниченный рост таблицы | Регламент/партиционирование |
| 3.4 | `DELETE` не идемпотентен (повтор → 400) | Ломает ретраи клиентов | Трактовать 400 как «уже отозван» |
| 3.5 | 401/429 без JSON и `Retry-After` | Некрасивые ошибки в SPA | Свой `AuthenticationEntryPoint` |
| 3.6 | `touchLastUsed` — UPDATE на каждый успешный запрос | Лишняя нагрузка на БД | Кеш/отложенная запись |
| 3.7 | Пагинация аудита считается `offset / limit` | Некратные offset игнорируются; `limit<=0` → 20 записей с нуля | `offset`, кратный `limit`, или расширение порта |
| 3.8 | `idx_api_token_prefix` дублирует индекс уникального ограничения | Лишняя запись при INSERT/UPDATE | `DROP INDEX idx_api_token_prefix` |
| 3.9 | `scope_mapping` допускает логические дубли (`tenant_id IS NULL`) | Разрастание маппингов, неоднозначность | Upsert по нормализованному ключу |
| 3.10 | Нет `@Version`/оптимистичных блокировок | Конкурентные изменения — «последний победил» | Внешняя синхронизация/аккуратность |
| 3.11 | Длинные `endpoint`/`user_agent` (> 512) ломают вставку аудита | Тихая потеря событий | Обрезать в своём `AuditRecorder` |
| 3.12 | Нет FK у `api_token_audit_log.token_id` | «Осиротевшие» записи | Учитывать в отчётах |
| 3.13 | `ApiTokenResponse` не содержит `slidingTtlSeconds` и параметров лимита | UI не может их показать | Расширить DTO |
| 3.14 | Argon2id (64 МиБ, 3 итерации) проверяется на каждом запросе | CPU/память на горячем пути | Кеш проверки, свои параметры хешера |
| 3.15 | `PUBLIC_PATHS` UI не входят в `securityMatchers` | `/css/**`, `/error` могут требовать аутентификации | Добавить в `securityMatchers`/`WebSecurityCustomizer` |
| 3.16 | Демо-UI: нет i18n, тёмной темы, пагинации; `/ui/scopes` без flash | Не готов к продакшену как есть | Свой UI или доработка |

## 4. Ограничения архитектуры (осознанные)

| Ограничение | Причина | Комментарий |
|---|---|---|
| Нет таблицы пользователей/владельцев | Библиотека не управляет пользователями | `owner_id` — строка из security context |
| Нет автоматического удаления токенов | Аудит и история важнее | Удаление — только через БД или доработку |
| Ядро без Spring | Переносимость и тестируемость | Транзакции только в декораторе авто-конфигурации |
| In-memory лимитер | Отсутствие внешних зависимостей в MVP | Redis заявлен как post-MVP |
| Формат токена фиксирован | Совместимость | Смена формата — только своим аутентификатором |
| Публикации артефакта нет | Не настроен `maven-publish` | Подключение через `includeBuild` |

## 6. Roadmap

### 6.1. Заявлено в исходном плане (post-MVP)

| Пункт | Статус | Комментарий |
|---|---|---|
| Redis-реализация `RateLimiter` | ❌ не сделано | Порт готов, реализации нет; `rate-limit.backend` не читается |
| Партиционирование `api_token_audit_log` | ❌ не сделано | Требуется для промышленной эксплуатации |
| Публикация в Maven Central / Nexus | ❌ не сделано | `maven-publish` не настроен |
| Admin UI | ✅ сделано сверх плана | Реализован server-rendered UI в `openapi-tokens-sample-ui` |
| Security-ревью (энтропия, параметры хеша, маскирование PII) | ⚠️ частично | `ip`/`user_agent` пишутся без маскирования; ревью не оформлено |

### 6.2. Предлагаемый план работ

**Этап 1 — безопасность и корректность (must have для продакшена)**

1. Ограничение допустимых скоупов при создании токена (🔴 1.1).
2. Тесты фильтра аутентификации, цепочки безопасности и обработчика ошибок (🟠 2.5).
3. Запрет/перезапись `tenantId` из запроса (🟠 2.4).
4. Тесты `ProblemDetail`-контрактов и валидации свойств.

**Этап 2 — эксплуатационная зрелость**

5. Планировщик перевода в `EXPIRED` или вычисляемый фактический статус (🟠 2.1).
6. Освобождение квоты при отзыве либо операция удаления токена (🟠 2.2).
7. Ротация/партиционирование журнала аудита (3.3).
8. Метрики (Micrometer): создания, отказы, лимиты, ошибки аудита.
9. Единый формат ошибок аутентификации (JSON + `Retry-After`) (3.5).

**Этап 3 — масштабирование**

10. Внешний (Redis) `RateLimiter` (3.1).
11. Пагинация и фильтрация административного API (🟠 2.6, 3.7).
12. Устранение N+1 в `findAll()` (3.7), удаление дублирующего индекса (3.8).
13. Кеширование результата проверки токена (3.14).

**Этап 4 — удобство и развитие**

14. Приведение конфигурации в порядок: реализовать или удалить мёртвые свойства (🟠 2.3).
15. Аудит жизненного цикла (создание/отзыв/блокировка) (3.2).
16. Расширение DTO (`slidingTtlSeconds`, параметры лимита) (3.13).
17. Настройка `maven-publish` и публикация артефакта.
18. Чистка документации и кода: README, `PUBLIC_PATHS`, неиспользуемые зависимости, устаревшие комментарии.
19. Расширение BDD-покрытия на REST/UI-потоки и теги (`@smoke`, `@regression`).
20. Мультитенантность: фильтрация токенов по тенанту, тесты.

## 7. Что можно сделать без изменений в библиотеке

| Задача | Как |
|---|---|
| Ограничить скоупы | Валидация в своём контроллере/фильтре |
| Избавиться от просроченных «активных» токенов | Своя задача перевода в `EXPIRED`/удаления |
| Распределённый лимит | Свой `RateLimiter` или лимит на API-gateway |
| Аудит для SIEM | Свой `AuditRecorder` (например, с отправкой в Kafka/ClickHouse) |
| Хранение не в PostgreSQL | Свои реализации портов репозиториев |
| Единый JSON для 401/429 | Свой `AuthenticationEntryPoint` + своя цепочка безопасности |
| Уборка журнала | SQL-задача/партиции |
| Метрики | Micrometer-обёртки вокруг `ApiTokenService` |
| Интернационализация UI | Свой фронтенд |

## 8. Как предложить изменение

1. Сверьтесь с правилами `.cursor/rules/java-senior.mdc` (конструкторная инъекция,
   изоляция DTO и сущностей, BDD для бизнес-требований, LAZY-загрузка, `@Transactional`).
2. Для изменения поведения сначала добавьте тест (юнит/BDD), затем реализацию.
3. Изменения схемы БД — только новой Flyway-миграцией (нумерация после `V2`).
4. Обновляйте документацию вместе с кодом: этот сайт — источник истины
   (см. [Публикация документации](publishing.md#6-обновление-документации)).
