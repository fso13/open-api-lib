# Документация для бизнес-аналитика

Этот раздел описывает библиотеку **open-api-lib** на языке бизнеса: какие задачи она решает,
какие роли участвуют, какие правила действуют, что считается выполненным и какие ограничения
нужно учитывать при постановке требований. Технические детали вынесены в другие разделы.

---

## 1. Зачем это нужно бизнесу

Продукт предоставляет HTTP API. Партнёрам, CI/CD, скриптам и внутренним сервисам нужен
доступ **без человека за клавиатурой**. Если выдать им логин и пароль сотрудника, возникают
проблемы:

| Бизнес-проблема | Что даёт open-api-lib |
|---|---|
| Нельзя отозвать доступ у одного интегратора, не меняя пароль всем | У каждого интегратора свой токен, который отзывается точечно |
| Нет понимания, кто именно «сломал» API | Журнал аудита: какой токен, когда, откуда и в какой эндпоинт обращался |
| Интегратор получает больше прав, чем нужно | Скоупы: токен даёт только оговорённый набор прав |
| «Вечные» доступы не пересматриваются | Срок жизни токена (абсолютный и/или продлеваемый) |
| Один интегратор перегружает систему | Лимит запросов на токен |
| Каждый продукт делает это заново | Готовый переиспользуемый компонент: выпуск, отзыв, права, лимиты, аудит, готовый API |

**Ценность:** сокращение времени вывода интеграции на рынок и снижение риска неконтролируемого
доступа к API.

## 2. Глоссарий

| Термин | Значение |
|---|---|
| **API-токен** | Секретная строка для доступа к API без участия человека. Показывается один раз при выпуске |
| **Префикс** | Публичная часть токена (`atk_` + 8 символов). Видна в списках и логах, нужна для поиска |
| **Секрет** | Секретная часть токена. Хранится только в виде необратимого хеша |
| **Владелец (owner)** | Пользователь или сервис, которому принадлежит токен. Определяется из текущей аутентификации |
| **Скоуп (scope)** | Именованное разрешение, привязанное к токену (например, `payments:read`) |
| **Право (authority)** | Внутреннее разрешение приложения, которое проверяется в коде (например, `createPayment`) |
| **TTL** | Срок жизни токена. Абсолютный — до даты; скользящий — пока токен используется чаще, чем раз в N секунд |
| **Отзыв (revoke)** | Необратимое отключение токена |
| **Блокировка (block)** | Временное отключение токена администратором с возможностью вернуть |
| **Квота** | Максимальное число токенов у одного владельца |
| **Rate limit** | Ограничение частоты обращений по токену |
| **Аудит** | Журнал попыток использования токенов |
| **Тенант** | Изолированный «клиент»/организация, если продукт мультитенантный |

## 3. Роли и их возможности

| Роль | Кто это | Что может |
|---|---|---|
| **Владелец токена** | Аутентифицированный пользователь или сервис продукта | Создавать токены (в пределах квоты), видеть свои токены, смотреть статистику и аудит по своим токенам, отзывать свои токены |
| **Администратор** | Сотрудник поддержки/эксплуатации (роль `ADMIN` в продукте) | Видеть все токены всех владельцев, смотреть аудит любого токена, блокировать/разблокировать, принудительно отзывать |
| **Интегратор (потребитель токена)** | Внешняя система, CI, скрипт | Обращаться к API, предъявляя токен; прав больше, чем дано в скоупах, не имеет |
| **Бизнес-аналитик / владелец продукта** | — | Определяет перечень скоупов, квоты, сроки жизни, правила выдачи — через конфигурацию и продуктовые процессы |

!!! warning "В библиотеке нет управления пользователями"
    Список владельцев и их права — ответственность продукта. Библиотека лишь фиксирует
    идентификатор владельца (строку) и проверяет, что он обращается к своим токенам.

## 4. Функциональные возможности (на языке бизнеса)

### 4.1 Выпуск токена

Владелец создаёт токен, указывая:

| Параметр | Обязателен | Смысл для бизнеса |
|---|---|---|
| Название | Да | Чтобы человек понимал, для чего токен («CI биллинга», «Интеграция с CRM») |
| Описание | Нет | Дополнительный контекст |
| Скоупы | Да, минимум один | Какие действия разрешены |
| Дата окончания | Нет | До какого момента токен действителен |
| Скользящий TTL | Нет | Токен «умирает», если им не пользовались N секунд |
| Лимит запросов и окно | Нет (только вместе) | Сколько запросов допустимо за период |
| Тенант | Нет | Привязка к организации (в мультитенантном продукте) |

**Результат:** созданный токен с секретом, который показывается **ровно один раз**.

### 4.2 Просмотр и контроль

- Владелец видит список своих токенов со статусами и счётчиками (всего/активных/
  заблокированных/отозванных/истёкших).
- Владелец и администратор видят по каждому токену: метаданные, статистику использования
  и журнал обращений.
- Фильтры: по тексту (название, префикс, описание), по владельцу (админ), по статусу.

### 4.3 Управление жизненным циклом

| Действие | Кто | Обратимо | Условие |
|---|---|---|---|
| Отзыв (revoke) | владелец, администратор | ❌ нет | токен ещё не отозван |
| Блокировка (block) | администратор | ✅ да | токен активен |
| Разблокировка (unblock) | администратор | ✅ да | токен заблокирован |

### 4.4 Контроль доступа

- Токен действует только если он активен и не истёк.
- Скоупы токена превращаются в права приложения; код проверяет право перед выполнением операции.
- Превышение лимита частоты приводит к отказу в обслуживании запроса.
- Каждая попытка использования токена (успешная и неуспешная) фиксируется в журнале.

### 4.5 Справочник скоупов

Единый источник «какие скоупы существуют и что они означают»: используется в интерфейсе
создания токена, в документации для интеграторов и в административной консоли.
Описания задаются конфигурацией или данными в БД; данные в БД приоритетнее.

## 5. Бизнес-правила

| ID | Правило | Источник |
|---|---|---|
| **BR-1** | В режиме `identity` каждый скоуп токена даёт ровно одно право с тем же именем | `scopes-resolution.feature` |
| **BR-2** | В режиме `mapped` скоуп токена заменяется набором прав из маппинга (один скоуп → много прав) | `scopes-resolution.feature` |
| **BR-3** | Для одного и того же скоупа запись маппинга в БД **заменяет** (не дополняет) настройку из конфигурации | `scopes-resolution.feature` |
| **BR-4** | Владелец в пределах квоты может создать токен; секрет возвращается один раз; хранится только хеш; статус нового токена — «активен» | `create-token.feature` |
| **BR-5** | Если у владельца уже максимальное число токенов, создание отклоняется и токен не сохраняется | `create-token.feature` |
| **BR-6** | Владелец может отозвать свой активный токен; статус становится «отозван» и токен больше не действует | `revoke-token.feature` |
| **BR-7** | Токен, у которого истёк абсолютный или скользящий срок, не проходит проверку (отказ) | `TokenExpiryTest` |
| **BR-8** | Успешное использование токена продлевает скользящий срок | `DefaultApiTokenAuthenticatorTest`, `DefaultApiTokenServiceTest` |
| **BR-9** | Заблокировать можно только активный токен; разблокировать — только заблокированный | `ApiTokenInvariantsTest` |
| **BR-10** | Повторный отзыв уже отозванного токена — ошибка (не идемпотентно) | `ApiTokenInvariantsTest` |
| **BR-11** | Чужой токен для владельца «не существует»: попытка обращения даёт «не найдено», а не «доступ запрещён» | `DefaultApiTokenServiceTest`, UI-тесты |
| **BR-12** | Администратор видит и управляет токенами всех владельцев | `AdminApiTokenControllerTest`, UI-тесты |
| **BR-13** | Каждая попытка использования токена фиксируется в журнале (успех, отказ, превышение лимита) | `AsyncAuditRecorderTest` |
| **BR-14** | Превышение лимита частоты — отдельный тип отказа (не «неверный токен») | `Bucket4jRateLimiterTest`, `DefaultApiTokenAuthenticatorTest` |
| **BR-15** | Токен, использованный в качестве учётных данных, позволяет управлять только своими токенами | `InternalTokenOwnerResolver` (владелец из токена) |
| **BR-16** | Квота считается по **всем** токенам владельца, включая отозванные и заблокированные | `JpaApiTokenRepository#countByOwnerId` (без фильтра по статусу) |

!!! warning "BR-16 — важное следствие для бизнеса"
    Отозванный токен продолжает «занимать место» в квоте. Если пользователь отозвал токен и
    хочет выпустить новый, лимит придётся поднять или обратиться в поддержку (удаления токенов
    в продукте нет). Обсудите: либо увеличить квоту, либо инициировать доработку
    («освобождать квоту при отзыве»).

## 6. Сценарии использования

### UC-1. Выдать доступ внешнему интегратору

1. Интегратор запрашивает доступ к API.
2. Аналитик определяет нужный скоуп (например, `payments:read`).
3. Владелец (сотрудник, ответственный за интеграцию) создаёт токен с этим скоупом,
   указывает дату окончания и лимит частоты.
4. Интегратор получает секрет и настраивает его в своей системе.
5. Через N месяцев токен истекает или отзывается по завершении работ.

**Ожидаемый результат:** доступ есть только у этого интегратора, только к оговорённым
операциям, и его можно отозвать в любой момент.

### UC-2. Подключить CI/CD

1. Инженер создаёт токен с техническим именем («CI биллинга»).
2. Указывает скользящий TTL (например, 1 час) — токен отключается сам, если пайплайн перестал
   ходить в API.
3. Указывает лимит (например, 100 запросов в минуту), чтобы пайплайн не «задушил» прод.
4. Секрет сохраняется в секретах CI.

### UC-3. Расследовать инцидент

1. Поступает жалоба на аномальные запросы к API.
2. Администратор открывает список всех токенов, находит подозрительные по владельцу/статусу.
3. Смотрит аудит: время, метод, эндпоинт, IP, User-Agent, результат.
4. Блокирует токен (если нужно разобраться) или отзывает принудительно.

**Результат:** подтверждение или опровержение гипотезы и немедленная нейтрализация доступа.

### UC-4. Отозвать доступ у уволенного сотрудника

1. Администратор находит все токены владельца.
2. Принудительно отзывает каждый.

**Ограничение:** автоматического массового отзыва «все токены пользователя» в API нет —
это последовательность вызовов или доработка.

### UC-5. Перевыпустить токен с новым лимитом

1. Владелец создаёт новый токен с нужным лимитом.
2. Переключает интеграцию на новый токен.
3. Отзывает старый.

**Ограничение:** старый токен остаётся в квоте (BR-16).

### UC-6. Опубликовать справочник скоупов для интеграторов

1. Аналитик согласует список скоупов и их описания.
2. Описания попадают в конфигурацию или в таблицу справочника.
3. Интеграторы получают актуальный перечень через API справочника/страницу документации.

## 7. Критерии приёмки (BDD)

Ниже — принятые в проекте бизнес-сценарии (Gherkin). Они же — источник правил BR-1…BR-6.

### Разрешение скоупов

```gherkin
Feature: Scope resolution
  As a product integrating API tokens
  I want token scopes resolved to project authorities
  So that access control matches the configured mode

  Scenario: Identity mode keeps scopes 1:1
    Given scope mode is "identity"
    And a token with scopes "payments:read,payments:write"
    When scopes are resolved for tenant "tenant-a"
    Then the authorities should be "payments:read,payments:write"

  Scenario: Mapped mode expands scopes from config
    Given scope mode is "mapped"
    And config mapping "payment" to "createPayment,readPayment"
    And a token with scopes "payment"
    When scopes are resolved for tenant "tenant-a"
    Then the authorities should be "createPayment,readPayment"

  Scenario: Mapped mode prefers DB mappings over config for the same token scope
    Given scope mode is "mapped"
    And config mapping "payment" to "createPayment"
    And DB mapping "payment" to "refundPayment" for tenant "tenant-a"
    And a token with scopes "payment"
    When scopes are resolved for tenant "tenant-a"
    Then the authorities should be "refundPayment"
```

### Создание токена

```gherkin
Feature: Create API token
  As an authenticated owner
  I want to create an API token
  So that I can automate access to the API

  Scenario: Successfully create token
    Given an owner "owner-1" with 0 existing tokens
    And the max tokens per owner is 10
    When the owner creates a token named "ci" with scopes "read,write"
    Then the raw token should be returned once
    And the stored token should contain a hash not the secret
    And the token status should be "ACTIVE"

  Scenario: Reject when quota exceeded
    Given an owner "owner-1" with 10 existing tokens
    And the max tokens per owner is 10
    When the owner creates a token named "ci" with scopes "read"
    Then token creation should fail with quota exceeded
```

### Отзыв токена

```gherkin
Feature: Revoke API token
  As an authenticated owner
  I want to revoke my API token
  So that it can no longer be used

  Scenario: Successfully revoke token
    Given an owner "owner-1" owns an active token
    When the owner revokes the token
    Then the token status should be "REVOKED"
```

!!! note "Сценарии, которых пока нет в BDD"
    Покрыты автотестами, но не оформлены как Gherkin (кандидаты для расширения приёмочных
    критериев): блокировка/разблокировка, истечение TTL и продление скользящего окна,
    превышение лимита частоты, административные операции, правила аудита, доступ к чужому
    токену, ограничение списка допустимых скоупов.

| Экран | Кому | Назначение |
|---|---|---|
| Вход | всем | Логин по логину/паролю (сессия) |
| Мои токены | владельцу | Список, поиск, фильтр по статусу, счётчики |
| Создание токена | владельцу | Форма выпуска, подсказки по скоупам |
| Секрет токена | владельцу (однократно) | Показ секрета и кнопка «Скопировать» |
| Карточка токена | владельцу | Метаданные, статистика, журнал (50 записей), отзыв |
| Справочник скоупов | любому аутентифицированному | Скоупы и их описания |
| Все токены | администратору | Список всех, фильтры по тексту/владельцу/статусу, счётчики |
| Карточка (админ) | администратору | Метаданные владельца, статистика, аудит (100 записей), блокировка/разблокировка/отзыв |

!!! warning "UI — демонстрационный, а не продукт"
    Экраны находятся в демо-модулях и служат образцом/референсом. Для продукта
    предполагается собственный интерфейс на REST API (см.
    [Фронтенд-разработчику](frontend.md)). Экраны и все надписи — только на русском языке,
    без интернационализации.

| Принудительный отзыв | администратор | Необратимое отключение |
| Справочник скоупов | любой аутентифицированный | Скоупы и описания |

## 9. Отказы и сообщения

| Ситуация | Что увидит пользователь | Понятность |
|---|---|---|
| Квота исчерпана | Ошибка «превышена квота токенов», HTTP 409 | ✅ понятно, но без подсказки «отзовите старый токен» |
| Токен не найден / чужой | «Не найдено», HTTP 404 | ✅ намеренно скрываем существование |
| Неверный статус перехода (повторный отзыв, блокировка неактивного) | «Недопустимый запрос», HTTP 400 | ⚠️ текст технический (на английском) |
| Пустой набор скоупов | «Недопустимый запрос», HTTP 400 | ⚠️ технический текст |
| Ошибка валидации формы | Сообщение первой ошибки поля | ✅ в UI — по-русски |
| Неверный/истёкший/заблокированный токен | «Unauthorized», HTTP 401 | ⚠️ без деталей (намеренно) |
| Превышен лимит частоты | «Rate limit exceeded», HTTP 429 | ⚠️ без указания, когда повторить |

**Рекомендация для постановки задач:** если интеграторам нужны понятные тексты и заголовок
«когда повторить», это отдельное требование к продукту (библиотека сейчас отдаёт технический
ответ на 401/429).

## 10. Ограничения, риски и открытые вопросы

### Ограничения (учитывать при планировании)

| Ограничение | Влияние на бизнес |
|---|---|
| Нет физического удаления токенов | Квота «не освобождается»; список растёт |
| Нет фонового истечения: просроченный токен остаётся со статусом «активен» | В отчётах и интерфейсах нельзя полагаться только на статус; нужен расчёт по срокам |
| Нет фильтрации и постраничности в административном API | При большом числе токенов админка работает медленно |
| Аудит фиксирует только использование токенов, не выпуск/отзыв | Нельзя ответить «кто и когда выдал токен» по журналу |
| Журнал не чистится автоматически | Рост БД; нужна регламентная процедура |
| Лимит частоты работает по каждому узлу приложения отдельно | В кластере фактический лимит умножается на число узлов |
| Секрет нельзя восстановить | Утерянный токен только перевыпускается |
| Нет интернационализации и тёмной темы в демо-UI | Для международного продукта нужен свой фронтенд |
| Нет публикации артефакта в общий репозиторий | Подключение требует участия разработки |

### Риски (требуют решения до продакшена)

| Риск | Описание | Рекомендация |
|---|---|---|
| 🔴 **Повышение привилегий** | Пользователь может запросить произвольный скоуп; в режиме `identity` это позволяет выдать себе права администратора | Запретить произвольные скоупы (белый список) — обязательное требование к продукту |
| 🟠 **Подмена тенанта** | Тенант можно указать в запросе при создании токена | Убирать/перезаписывать поле на стороне продукта |
| 🟠 **Просроченные токены выглядят активными** | Может ввести в заблуждение поддержку и аудит | Требовать отображения «фактического» статуса (по срокам) в интерфейсе |
| 🟠 **Аудит без контроля доступа к записям** | Журнал не описывает выпуск токенов | Дополнять событиями продукта, если это требование комплаенса |
| 🟡 **«Мёртвые» настройки** | Часть параметров (`audit.*`, `rate-limit.backend`, `token.default-ttl`) не влияет на поведение | Не закладывать их в функциональные требования как реальные переключатели |

### Открытые вопросы к бизнесу

1. Сколько токенов должен иметь один владелец по умолчанию и нужно ли освобождать квоту при отзыве?
2. Нужен ли срок жизни по умолчанию (сейчас его нет — токен бессрочный, если дату не указать)?
3. Нужно ли уведомлять владельца об истечении/блокировке токена?
4. Требуется ли журнал выпуска и отзыва токенов (комплаенс)?
5. Нужны ли понятные тексты и «когда повторить» для ошибок 401/429?
6. Кто и как утверждает перечень скоупов и их описания?
7. Нужна ли поддержка нескольких организаций (тенантов) в интерфейсе?
8. Каков требуемый срок хранения журнала обращений?

## 11. Что не входит в объём

| Не входит | Комментарий |
|---|---|
| Аутентификация пользователей, пароли, SSO | Ответственность продукта |
| Управление пользователями, ролями, организациями | Ответственность продукта |
| Уведомления (e-mail, мессенджеры) об истечении токенов | Не реализовано |
| Отчётность и дашборды по токенам | Только базовые счётчики и статистика по токену |
| Утверждение (approval) выдачи токенов, четырёхглазый принцип | Не реализовано |
| Оплата/биллинг по объёму запросов | Вне области |
| Продуктовый UI (дизайн, брендирование, локализация) | Демо-UI — только референс |
